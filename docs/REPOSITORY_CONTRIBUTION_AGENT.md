# 仓库持续贡献 Agent

记录日期：2026-09-13。初步需求已确认，首期按最小闭环进入实现。

## 想解决的问题

持续关注指定的 GitHub 仓库，发现适合参与的工作，让用户减少反复查看仓库、筛选 issue 和准备上下文的时间。长期希望从发现任务到完成贡献的整个流程逐步自动化。

## 初期范围

- 持续监控用户选定的仓库，发现新 issue。
- 判断 issue 是否适合用户参与、是否已有其他人处理，筛出值得接手的任务。
- 按仓库的协作规则帮助用户认领，例如留言表达处理意愿或请求分配；具体机制待确定。
- 整理问题背景、相关信息和认领状态，交给用户开始开发。

初期由用户承担实际开发。监控频率、筛选条件、通知方式，以及认领前是否需要用户确认，尚未确定。

## 长期目标

逐步覆盖理解问题、准备开发环境、修改代码、验证、提交 PR、跟进 review 和修订，直到贡献得到明确处理结果。自动执行和人工确认的边界按阶段确定。

任务来源也可以扩展到主动发现问题：检查仓库中的潜在 bug、测试缺口或其他值得改进的地方，验证后形成可执行任务，再进入同一套贡献流程。主动发现属于后续方向，首期是否包含尚未决定。

## 后续需要明确

- 首批监控哪些仓库，什么样的任务值得接手，如何判断与用户能力和时间安排匹配。
- 如何识别已有负责人、重复任务以及仓库特有的认领规则。
- 在哪里接收通知和查看任务；是否作为 Repolane 的功能，或独立运行。
- 持续监控运行在哪里、如何触发；使用什么身份和权限执行操作。
- 各阶段哪些动作自动执行，哪些需要用户确认；遇到失败、冲突或长期无回应时如何处理。

## 下一步

围绕一个实际仓库，明确首期“监控 → 筛选 → 认领 → 交给用户开发”的具体流程和完成标准。

这份记录用于长期恢复讨论。用户已授权首期开发；对外认领、提交 PR 等自动操作尚未授权。

## 首期实施决定

用户已认可先验证“发现 → 推荐”，并授权开发。第一步已实现独立命令行工具、本地 SQLite 和可配置模型接口。随后用户确认第二版页面示意图并授权接入 App：新增“贡献机会”页面与配置弹窗，Rust 后台负责监控，复用 App 的 GitHub 登录。两种入口均输出推荐及认领草稿；用户手动完成 GitHub 留言和实际开发。自动认领、主动扫描代码和自动开发仍未启动。

使用方式和能力边界见[监控工具说明](OPPORTUNITY_MONITOR.md)。首批仓库和模型服务尚待用户选择，当前开发验证使用模拟数据。
